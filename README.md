# 🔐 プライバシー設計と透明性･安全性

**CipherCapsule** は、メッセージ本文と添付ファイルを強力な認証付き暗号で保護し、受信者がパスワードを入力して内容を閲覧できる、Windows向けの自己復号型暗号化メッセージ作成ソフトウェアです。

本ソフトウェアは、**プライバシーの保護、暗号処理の透明性、データの完全性、利用者による制御**を重視して設計されています。

## 🛡️ 1. プライバシー保護の基本方針

| 保護項目 | 実装内容 |
|---|---|
| 🔒 メッセージ本文 | TEXT・HTMLともに認証付き暗号で保護 |
| 📎 添付ファイル | ファイル内容を分割して暗号化 |
| 🏷️ 添付ファイル名 | 暗号化されたマニフェスト内で保護 |
| 🔑 パスワード | 暗号鍵導出に使用し、生成EXEに平文保存しない |
| 🗝️ 暗号鍵 | 暗号化ごとに新しいランダム鍵を生成 |
| 🌐 外部通信 | メッセージ表示に不要な外部通信を禁止 |
| 📝 設定ファイル | パスワード・本文・暗号鍵を保存しない |
| 🧩 HTML表示 | JavaScript実行・外部リソース読込みを制限 |
| 📋 コピー制御 | 作成者がViewerでの通常のコピー操作を許可・禁止できる |
| ✅ 改ざん検出 | 認証タグとハッシュによって不正な変更を検出 |
| 🔍 ソースコード | 公開ソースと依存関係情報により設計を検証可能 |

CipherCapsule自身には、メッセージをサーバーへアップロードする機能、ユーザー行動を収集するテレメトリ、バックグラウンド更新、権限昇格、常駐・自動起動の仕組みを実装していません。

暗号化・復号処理はローカル環境で実行されます。

ただし、WindowsやWebView2 Runtimeなど、OS・外部コンポーネントが独自に行う処理や通信まで保証するものではありません。

### 🔑 パスワードの取扱い

CipherCapsuleは、入力されたパスワードからArgon2idによって暗号鍵を導出します。

パスワードそのものを暗号化EXEに埋め込んだり、INIファイルへ保存したりすることはありません。

Builderでは連続して暗号化EXEを作成できるように、暗号化成功・失敗・キャンセル後も入力したパスワードを保持します。

保持されるのは現在のアプリケーション起動セッション内だけです。

アプリケーション終了後にパスワードを復元する機能はありません。

暗号鍵や機密バッファは、利用を終えた段階で可能な範囲で消去します。ただし、.NETの管理メモリ、OSのページング、クリップボード、ブラウザーキャッシュなどから、過去の機密データを完全消去できる保証はありません。

**共有パソコンでは、使用後にCipherCapsuleを終了してください。**

### 🌐 HTML表示と外部リンクの安全性

HTML本文はWebView2で表示しますが、受信したHTMLを一般的なWebページとして無制限に実行することはありません。

- JavaScriptの実行を禁止
- iframe・フォーム・埋込みスクリプト等を除去
- 不必要な外部リソース要求を遮断
- 外部画像の自動ダウンロードを禁止
- HTMLからのファイルダウンロードを制限
- 不要なブラウザー権限を拒否
- ホストオブジェクトへのアクセスを禁止
- HTML描画にContent Security Policy（CSP）を適用

外部リンクはHTTP・HTTPSに限定しています。

リンクがクリックされると確認ダイアログが表示され、利用者が許可した場合のみ、Windowsの既定ブラウザーで開きます。

仕様ダイアログの固定GitHub URLは、利用者のクリックで直接既定ブラウザーへ渡します。受信HTML本文のリンクは上記の確認を維持します。

リンク先のサイトをCipherCapsule内のWebView2で直接閲覧させる仕組みではありません。

なお、利用者が外部リンクを開いた後の通信・Cookie・アクセス記録等は、開いたブラウザーとリンク先Webサイトの管理対象になります。

### 📎 添付ファイルと平文データの保護

添付ファイルは暗号化された状態でEXE内へ格納されます。

受信者がパスワード認証に成功しても、添付ファイルを自動実行することはありません。

添付ファイルをディスクへ復号保存するのは、受信者が明示的に保存操作を行った場合です。

保存時には、認証付き復号と安全な一時ファイル処理を実施します。

ただし、保存されたファイルは通常の平文ファイルです。保存後の保護は、利用者のWindows環境、アクセス権、BitLocker等の設定に依存します。

### 🔍 透明性とセキュリティ上の限界

CipherCapsuleは、暗号化データの機密性と改ざん検出を目的としています。

一方、以下を保証するものではありません。

- スクリーンショットや外部カメラによる撮影の防止
- OCRによる文字の取得防止
- 管理者権限を持つ第三者からの完全な保護
- マルウェアに感染した端末での機密保持
- OSメモリ・ページファイル・キャッシュの完全消去
- 送信者の本人確認
- 未署名EXEのプログラム部分が改ざんされていないことの自動保証

特に重要なのは、**暗号化メッセージの認証と、EXEプログラムそのものの真正性は別問題**という点です。

悪意ある第三者がViewerの実行コードを改変した場合、入力されたパスワードを盗むプログラムに置き換えられる可能性があります。

信頼できない送信元から受け取ったEXEを安易に実行しないでください。

CipherCapsuleの正式EXEは、現行版ではAuthenticodeによるコード署名を行っていません。Windows SmartScreenやセキュリティソフトウェアの警告が表示される場合があります。

Windowsの保護機能を無効化して使用することは推奨しません。

# 🧬 暗号アルゴリズムと暗号化アーキテクチャ

CipherCapsuleは、複数の暗号技術を組み合わせたハイブリッドな鍵管理構造を採用しています。

暗号処理には、実績のある暗号ライブラリ **libsodium** を使用しています。

暗号アルゴリズムを独自に設計・実装するのではなく、libsodiumの公開APIを利用しています。

## 🔬 採用する暗号技術一覧

| 用途 | アルゴリズム・仕様 |
|---|---|
| パスワードベース鍵導出 | **Argon2id v1.3** |
| KDF演算パラメータ | `opslimit = 3` |
| KDFメモリ使用量 | 256MiB |
| KDF Salt | 128bit（16byte） |
| データの認証付き暗号化 | **XChaCha20-Poly1305** |
| 対称暗号鍵長 | 256bit（32byte） |
| XChaCha20-Poly1305 nonce | 192bit（24byte） |
| 認証タグ長 | 128bit（16byte） |
| マスター鍵 | 256bitランダムDEK |
| 用途別鍵導出 | libsodium `crypto_kdf` |
| 添付ストリーム暗号化 | `crypto_secretstream_xchacha20poly1305` |
| 添付分割サイズ | 最大1MiB／チャンク |
| 添付暗号文整合性確認 | SHA-256 |
| 生成EXE／CCAP全体のチェックサム | SHA-512／SHA-256 |
| 乱数生成 | libsodium `randombytes_buf` |

## 1. 🔑 Argon2id v1.3 — パスワードからの鍵導出

ユーザーが入力するパスワードは、そのまま暗号鍵として使用されません。

CipherCapsuleは、パスワードとランダムSaltを入力として、Argon2idによって256bitの鍵暗号化鍵（KEK：Key Encryption Key）を導出します。

```text
ユーザーパスワード
        │
        ├── ランダムSalt（16byte）
        │
        ▼
  Argon2id v1.3
  memory = 256MiB
  opslimit = 3
        │
        ▼
      KEK（256bit）
```

Argon2idは、メモリ使用量を必要とするパスワードベース鍵導出関数です。

計算量だけでなくメモリ資源も消費させることで、大量のパスワード候補を並列評価する攻撃のコストを高める設計です。

CipherCapsuleでは、1回の鍵導出につき256MiBのメモリパラメータを設定しています。

`opslimit = 3`はlibsodiumへ渡す演算コストパラメータであり、暗号強度が3倍になる、または必ず3回の単純なハッシュ計算だけを行うという意味ではありません。

Saltは暗号化処理ごとに新しく生成されます。

これにより、同じパスワードを複数のメッセージに利用しても、異なるSaltからKEKが導出されます。

**Argon2idは弱いパスワードを強いパスワードへ変換する魔法ではありません。** 短いパスワードや推測されやすい語句は、オフライン辞書攻撃・総当たり攻撃の対象となります。

長く、予測困難なパスフレーズの使用を推奨します。

## 2. 🔐 XChaCha20-Poly1305 — 認証付き暗号化

CipherCapsuleの中心的な暗号技術は、**XChaCha20-Poly1305**です。

これは、ストリーム暗号を基礎とするChaCha20系の暗号化技術と、Poly1305によるメッセージ認証を組み合わせたAEAD（Authenticated Encryption with Associated Data）方式です。

AEADは、単なるデータの秘匿だけでなく、暗号文と関連データの改ざん検出を提供します。

CipherCapsuleでは、libsodiumの次のAPIを使用します。

`crypto_aead_xchacha20poly1305_ietf_encrypt`

`crypto_aead_xchacha20poly1305_ietf_decrypt`

基本パラメータ：

- 対称鍵長：256bit
- nonce長：192bit
- 認証タグ長：128bit

XChaCha20では拡張された192bitのnonce空間を利用でき、適切な乱数生成と鍵管理の下で、ランダムnonceの衝突リスクを極めて低くできます。

Poly1305認証に失敗したデータは、正常な平文として受け入れられません。

認証タグを単なるエラーチェック値として扱わず、暗号学的な認証結果として検証します。

### AEADとAAD

CipherCapsuleでは、暗号化する平文だけでなく、暗号コンテナーのヘッダー情報をAAD（Additional Authenticated Data）として暗号処理へ関連付けます。

AADは暗号化されずに保持できる情報ですが、認証対象になります。

これによって、暗号文と関連するヘッダー情報を不正に組み替えた場合に、復号時の認証が失敗する設計です。

ただし、EXE全体のすべてのバイトがAEADの認証対象となるわけではありません。特にViewerプログラムそのものの真正性については、別途確認が必要です。

## 3. 🗝️ DEK・KEKによる鍵管理

CipherCapsuleは、パスワード由来の鍵を直接すべての添付ファイルへ使い回す構成ではありません。

暗号化ごとに新しい256bitのランダムDEK（Data Encryption Key）を生成します。

このDEKを、Argon2idから導出したKEKでXChaCha20-Poly1305により暗号化します。

この方式を一般に**鍵ラッピング（Key Wrapping）**と呼びます。

```text
                 ┌─────────────────────┐
                 │ ユーザーパスワード    │
                 └──────────┬──────────┘
                            │
                    Argon2id + Salt
                            │
                            ▼
                       KEK（256bit）
                            │
                            │ DEKを認証付き暗号化
                            ▼
ランダム生成 ────► DEK（256bit）
                            │
                            ├── マニフェスト用鍵
                            │
                            └── 添付ファイルごとの鍵
```

暗号化されたDEKと鍵導出に必要なSalt・nonce・パラメータは、コンテナー内に格納されます。

平文DEKは格納しません。

受信者は正しいパスワードからKEKを再導出し、認証付き復号によってDEKを取得します。

この構造により、暗号化処理ごとに独立したDEKを使用できます。

## 4. 🧩 用途別鍵導出と鍵分離

取得したDEKをそのまますべての処理へ流用するのではなく、libsodiumの`crypto_kdf_derive_from_key`を利用して用途別の256bitサブキーを導出します。

このKDFは、libsodiumのBLAKE2bベースの鍵導出機構を利用します。

CipherCapsuleでは、用途を区別するために8byteのコンテキスト識別子とサブキーIDを使用します。

| 用途 | コンテキスト | サブキーID |
|---|---|---|
| マニフェスト暗号化 | `CCMANIF1` | `0` |
| 添付ファイル暗号化 | `CCATTCH1` | `1`以降 |

添付ファイルごとに異なるサブキーIDを使用します。

これにより、マニフェストと各添付ファイルの暗号処理を暗号学的に分離します。

鍵分離は、暗号鍵の誤用や異なるデータ形式間の不適切な鍵共有を避けるための重要な設計原則です。

## 5. 📎 crypto_secretstream_xchacha20poly1305 — 添付ファイル暗号化

添付ファイルには、libsodiumの次のストリーム暗号化APIを使用します。

`crypto_secretstream_xchacha20poly1305`

これは大容量データを順次暗号化・復号するための認証付きストリーム処理機構です。

CipherCapsuleは、添付ファイル全体を必ずしも一度にメモリへ展開せず、最大1MiBのチャンクに分割して処理します。

各チャンクには認証情報が付与されます。

ストリームの最後には、`TAG_FINAL`を指定します。

これにより、復号側でストリームの終了状態を検証します。

```text
添付ファイル
     │
     ▼
最大1MiB単位に分割
     │
     ├── チャンク1 ── AEAD暗号化・認証
     ├── チャンク2 ── AEAD暗号化・認証
     ├── チャンク3 ── AEAD暗号化・認証
     │
     └── 最終チャンク
                  └── TAG_FINAL
```

libsodiumのsecretstreamでは、24byteのストリームヘッダーを使用し、各チャンクに17byteの暗号化オーバーヘッドが加わります。

復号処理では、各チャンクの認証に加え、最終タグとストリーム構造を確認します。

認証に失敗した添付ファイルは正常なファイルとして確定保存しません。

## 6. 📋 認証付きマニフェスト

CipherCapsuleは、本文と添付ファイルに関する情報をマニフェストとして管理します。

マニフェストには主に以下の情報が含まれます。

- 本文形式（TEXT／HTML）
- メッセージ本文
- コピー許可設定
- 添付ファイル名
- 添付ファイルサイズ
- 暗号化添付の位置・長さ
- 添付暗号文のSHA-256

このマニフェスト全体をXChaCha20-Poly1305で認証付き暗号化します。

これにより、本文の書換えだけでなく、添付ファイルの名前、サイズ、並び、暗号文との対応関係などに対する不正な変更も検出対象になります。

なお、暗号化EXEの構造を読み取るために必要な一部の情報は平文です。

例えば、コンテナーのバージョン、KDFパラメータ、Salt、nonce、添付件数、データ長等は、必要に応じてヘッダーから確認できます。

**「すべてのメタデータが秘匿される」という仕様ではありません。**

## 7. 🛡️ SHA-256・SHA-512と完全性検証

CipherCapsuleは、暗号学的認証とハッシュによる整合性確認を組み合わせています。

ただし、それぞれの用途は異なります。

### SHA-256

各添付ファイルの暗号化されたストリーム領域についてSHA-256を計算し、そのハッシュ値を認証付きマニフェストに格納します。

復号時は暗号文のハッシュを再計算し、記録値と比較します。

これにより、添付暗号文の置換・欠落・破損を、チャンク復号の前段階でも検出できます。

さらに実際の保存時には、secretstreamによる各チャンクの認証を行います。

SHA-256自体は認証付き暗号ではありません。暗号文の認証と組み合わせることで、コンテナーの整合性確認に利用しています。

### SHA-512

Builderでは、暗号化EXE／CCAPの生成時にSHA-512とSHA-256のチェックサムファイルを独立選択して出力できます。

初期設定ではONです。

例：

```text
SecureMessage.exe
SecureMessage.exe.sha512
```

SHA-512とSHA-256は、最終的に生成されたEXE／CCAPファイル全体を対象として計算します。

チェックサムファイルは、128桁の16進数ハッシュ値と対象ファイル名を含む形式です。

PowerShellでは次のように照合できます。

```powershell
Get-FileHash -LiteralPath ".\SecureMessage.exe" -Algorithm SHA512
Get-Content -LiteralPath ".\SecureMessage.exe.sha512"
```

両者のハッシュ値が一致すれば、比較した2つのデータは同一のSHA-512ダイジェストを持つことが確認できます。

ただし、EXEとチェックサムファイルの両方が攻撃者に置き換えられた場合、SHA-512の一致だけでは攻撃を見破れません。

信頼できる別経路で入手したハッシュ値との比較や、信頼できるコード署名等による真正性確認が重要です。

**SHA-512は暗号化アルゴリズムでも電子署名でもありません。**

# 🚀 使い方

## ✉️ 暗号化メッセージを作成する

1. `CipherCapsule_v1.1.9.exe`を起動します。
2. メッセージ形式としてTEXTまたはHTMLを選択します。
3. 本文を入力します。
4. 必要に応じて添付ファイルを登録します。
5. テキストコピーの許可・禁止を指定します。
6. パスワードを入力します。
7. 「自己展開アーカイブの作成」をON（EXE）／OFF（CCAP）で選び、「暗号化する」をクリックします。
8. Windowsの保存ダイアログでEXE／CCAPの保存先を指定します。
9. 暗号化完了後、生成されたファイルを確認します。

SHA-512／SHA-256出力を有効にした分のチェックサムも作成されます。OFFでは既存のチェックサムを自動削除しません。

暗号化後も、Builderを終了するまではパスワードが保持されるため、同じパスワードで続けて別のメッセージを作成できます。

ただし、同じパスワードの使い回しより、用途ごとの強力で独立したパスワードを使用することを推奨します。

## 🔓 暗号化メッセージを閲覧する

1. 送信元を確認した自己復号EXEを直接起動するか、Builderの「暗号化ファイルを開く…」または画面内D&DからCCAPを開きます。
2. パスワードを入力します。
3. 正しいパスワードであればメッセージが表示されます。
4. HTMLリンクは確認後に既定ブラウザーで開けます。
5. 添付ファイルは必要なものを選択して保存します。

パスワードは、可能であればEXEファイルとは異なる通信経路で共有してください。

パスワードを紛失した場合に備えた復旧用バックドアやマスターキーは設けていません。

# 📦 自己復号EXEの構造と軽量化

CipherCapsuleが生成するEXEには、暗号化データと自己復号用Viewerが組み込まれています。

v1.1.1では、.NETのSingleFile圧縮機能を利用することで、Viewerを大幅に軽量化しました。

実測例：

| 比較項目 | 旧版 | v1.1.1 |
|---|---:|---:|
| 生成EXE | 約113.46MiB | 約50.29MiB |
| 起動時間中央値 | 0.634秒 | 0.765秒 |

同等のテストデータで、生成EXEの容量を約55.7%削減しました。

これは.NETの実行ファイル圧縮によるもので、暗号アルゴリズムや認証強度を弱めたものではありません。

ファイルサイズや起動時間は、本文・添付容量および実行環境によって変わります。

# ⚠️ セキュリティに関する重要な注意事項

### パスワード強度

短いパスワードや既知の単語は推測される可能性があります。

Argon2idの使用によって攻撃コストを増大させても、パスワードそのものの推測容易性は解消されません。

### EXEファイルの真正性

自己展開アーカイブを選んだ場合、本ソフトウェアが生成するメッセージはEXEファイルです。CCAPは実行コードを含まないデータファイルです。

EXEは単なる受動的な暗号化文書ではなく、Windows上で実行されるプログラムです。

**信頼できない相手から受け取ったEXEは実行しないでください。**

暗号化コンテナーの認証に成功しても、EXEの実行コードが元のCipherCapsule Viewerであることまで証明されるわけではありません。

### チェックサムと送信元確認

SHA-512チェックサムは、信頼できる経路で確認済みのハッシュと比較して初めて有効な検証手段になります。

チェックサムファイルをEXEと一緒に受け取っただけでは、送信者の本人確認にはなりません。

### データの完全消去

CipherCapsuleは不要になった機密バッファや一時データを可能な範囲で消去します。

ただし、ファイルシステム、SSD、OSの仮想メモリ、バックアップ、ブラウザープロファイル等からの復元可能性を完全に排除するものではありません。

### データ保存中の異常終了

暗号化EXE／CCAPと選択したSHA-512／SHA-256ファイルを、OS上で同時に原子的に確定させることは保証していません。

通常のエラー時には保護・復元処理を行いますが、電源断や強制終了では一時ファイル・退避ファイルが残る可能性があります。

配布前には最終EXEとチェックサムの一致を確認してください。
